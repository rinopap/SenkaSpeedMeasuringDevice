# 戦果時速計測機 Ver.2
## 開発仕様書・設計方針・実装計画

---

## 1. プロジェクト概要

### 1.1 プロジェクト名

SenkaSpeedMeasuringDevice（戦果時速計測機）

### 1.2 既存リポジトリ

https://github.com/rinopap/SenkaSpeedMeasuringDevice

### 1.3 開発背景

本ソフトウェアは、ブラウザゲーム「艦隊これくしょん」における提督経験値および艦娘経験値を取得し、単位時間当たりの戦果獲得量や艦娘経験値増加量をリアルタイムで表示するWindows向けデスクトップアプリケーションである。

現行バージョンはPythonおよびTkinterによって実装されている。

現在は、試製七四式電子観測儀（ElectronicObserver、以下74EN）の通信内容保存機能によって生成されるJSONファイルを監視し、必要な情報を取得している。

そのため、現状では74ENが導入されていなければ、新規の経験値データを取得できない。

今後は、この依存関係を解消するとともに、Windowsとの親和性、常駐時の軽量性、通信処理の拡張性および保守性の向上を目的として、C++への移行を行う。

---

## 2. 開発目的

本開発における主要な目的は以下のとおりである。

1. PythonからC++への移行。
2. 74ENを導入していない環境での単独動作の実現。
3. 74ENを使用している環境における併用の実現。
4. 74ENのウィンドウ取り込み機能との互換性確保。
5. 既存の戦果計測機能および艦娘経験値計測機能の維持。
6. 長時間常駐時の安定性および軽量性の向上。
7. 将来的な艦娘個体別育成管理機能への拡張性確保。
8. 大量の通信JSONファイルを生成する必要のない通信取得方式の確立。

ただし、74ENそのものを代替する専用ブラウザの開発は、本プロジェクトの目的としない。

また、必要性が明確でない機能の追加や過剰な抽象化は避け、戦果および経験値計測に特化した軽量なソフトウェアとする。

### 3.2 現行データ取得方式

74ENの通信内容保存機能により、以下のフォルダにAPIレスポンスが保存される。

`74en_responses/`

このフォルダに生成される `api_port@port.json` を対象として、watchdogによるファイル生成・更新イベントの監視を行う。

現行コードでは、ファイルの更新時刻およびファイルサイズをシグネチャとして利用し、同一ファイルの重複処理を抑制している。

取得イベントはキューに格納し、GUI側から500ミリ秒間隔で処理する。

### 3.3 APIレスポンスの構造

対象API：

`/kcsapi/api_port/port`

レスポンスの概略構造：

```json
{
  "api_result": 1,
  "api_data": {
    "api_basic": {
      "api_experience": 12345678
    },
    "api_ship": [
      {
        "api_id": 3415,
        "api_ship_id": 154,
        "api_lv": 99,
        "api_exp": [1000000, 0, 100]
      }
    ]
  }
}
```

上記の値は説明用のサンプルである。

実際のAPIレスポンスには、先頭に `svdata=` が付加される場合がある。また、UTF-8 BOMやURLエンコードされたデータへの対応も考慮する。

ただし、正常なJSONに対して無条件にURLデコードを行うと内容を破損させる可能性があるため、C++版では必要に応じてデコードする方式を検討すること。

### 3.4 提督経験値の取得

取得対象：

`api_data.api_basic.api_experience`

取得した累積提督経験値を `exp_log.csv` に保存する。

CSV形式：

```csv
timestamp,admiral_exp
2026-11-26T08:00:00,12345678
2026-11-26T08:05:00,12350678
```

既存CSVの読み込み互換性を維持すること。

### 3.5 戦果時速の計算

時刻 t1、t2 における累積提督経験値をそれぞれ E1、E2 とする。

戦果獲得量：

`S = (E2 - E1) × 7 / 10000`

戦果時速：

`V = S / 経過時間（時間単位）`

戦果換算係数 `7 / 10000` は現行実装を維持すること。

表示対象は以下の3区間とする。

- 前々時間帯
- 前時間帯
- 現在進行中の時間帯

例えば、現在時刻が08:34の場合：

```text
・06:00~07:00 戦果時速 45.23
・07:00~08:00 戦果時速 48.10
・08:00~08:34 戦果時速 51.67
```

数値は表示例である。

現行実装では、各時間帯の最初の観測記録と次の時間帯の最初の観測記録を使用し、実際の観測時刻間の経過時間に基づいて時速を算出する。

現在進行中の時間帯については、その時間帯の最初の観測記録と最新の観測記録を使用する。

観測記録が不足している場合、経過時間が0以下の場合、経験値差が負の場合には「記録不足」と表示する。

移植時にこの計算仕様を無断で変更しないこと。

### 3.6 艦娘経験値時速の計算

`api_data.api_ship` に含まれる全所持艦の `api_exp[0]` を取得し、その合計値を算出する。

累積艦娘経験値の合計を G とする。

`G = Σ api_exp[0]`

艦娘経験値時速：

`V_ship = (G2 - G1) / 経過時間（時間単位）`

記録先：

`ship_exp_log.csv`

```csv
timestamp,ship_total_exp
2026-11-26T08:00:00,123456789
2026-11-26T08:05:00,123556789
```

表示例：

```text
・06:00~07:00 Exp時速 125,000
・07:00~08:00 Exp時速 142,500
・08:00~08:34 Exp時速 138,200
```

なお、現行方式では艦娘の取得、解体、轟沈、近代化改修素材としての消費などによる所持艦構成の変化が、合計経験値に影響する。

したがって、現行の艦娘Exp時速は厳密には「全所持艦の総経験値の純増加速度」であり、必ずしも実際に獲得した経験値の総量とは一致しない。

初期移植では現行仕様を維持する。個体別差分による計算方式への変更は別途検討すること。

### 5.1 基本設計

データ取得層と戦果計算層を明確に分離する。

```text
┌─────────────────────────────┐
│        データ取得層          │
├─────────┬─────────┬─────────┤
│ 独自通信 │ 74EN    │将来的な │
│ 取得機能 │ JSON監視│拡張機能 │
└────┬────┴────┬────┴────┬────┘
     └─────────┼─────────┘
               ↓
┌─────────────────────────────┐
│       共通API処理層          │
│  API識別・JSON解析・検証     │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│        データ管理層          │
│  経験値記録・CSV・キャッシュ │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│          計算処理層          │
│  戦果時速・艦娘経験値時速    │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│            GUI              │
│   表示・設定・タスクトレイ   │
└─────────────────────────────┘
```

データ取得方法が変更された場合でも、計算処理、保存処理、GUIを変更する必要がない構造を目指す。

### 5.2 共通通信データ型

以下は設計上のインターフェース例である。

```cpp
struct ApiResponse {
    QString apiPath;
    QDateTime timestamp;
    QByteArray responseBody;
    QString eventId;
};
```

各データ取得モジュールは、取得した情報を共通データ型に変換し、共通API処理層へ渡す。

通信データの取得元に固有の処理を戦果計算クラスやGUIクラスに記述しないこと。

### 5.3 共通データ取得インターフェース

以下のような共通インターフェースを検討する。

```cpp
class ICaptureSource : public QObject {

        : QObject(parent) {}

    virtual ~ICaptureSource() = default;

    virtual void stop() = 0;
```

実際の実装では、スレッド間の型登録、オブジェクトの所有権、終了処理等を適切に管理すること。

## 6. 通信取得機能

### 6.1 基本方針

以下の2方式を主要な動作モードとする。

| モード | 内容 |
|---|---|
| 独立動作モード | 74ENを使用せず、APIレスポンスを取得する |
| 74EN互換モード | 74ENが保存したJSONを監視する |

独立動作モードについては、74ENを同時に使用できる構成も検討する。

利用者が設定画面からデータ取得方式を選択できるようにする。

原則として、同時に有効になる取得元は一つとし、同一通信イベントの二重記録を防ぐ。

### 6.2 独立動作モード：ローカルプロキシ方式

独自のローカルプロキシを用いて、ゲーム通信を中継しながら必要なAPIレスポンスを取得する方式を第一の検証対象とする。

以下は通信経路の構成案である。

```text
74ENを使用しない場合：

Chrome / Edge
      ↕
戦果時速計測機プロキシ
      ↕
艦これサーバー
```

待受アドレス：

`127.0.0.1`

待受ポート候補：

`40621`

ポート番号は固定仕様ではなく、利用者が設定可能なものとする。

対象APIを識別した後、レスポンスを共通API処理層へ渡す。

それ以外の通信については、必要な中継処理のみを行う。

ゲームへのリクエストおよびレスポンス内容の書き換えは行わない。

### 6.3 74ENとのプロキシ併用

74ENの上流・下流プロキシ設定を利用し、プロキシの直列接続を検討する。

第一候補となる構成：

```text
74EN内蔵ブラウザ
      ↕
74ENプロキシ
127.0.0.1:40620（例）
      ↕
戦果時速計測機プロキシ
127.0.0.1:40621（例）
      ↕
艦これサーバー
```

この構成では、ブラウザからのリクエスト方向を基準として、戦果時速計測機プロキシが74ENの上流に位置する。

ただし、74ENの現行バージョンにおける上流・下流プロキシの具体的な動作、HTTPS処理、証明書管理およびレスポンス本文の取得可否は、現時点では未検証である。

Codexは、74ENの公開ソースコードや公式ドキュメントを調査し、以下の項目を確認すること。

- 上流・下流プロキシ設定の正確な意味。
- 内蔵ブラウザとプロキシ間の通信経路。
- HTTP CONNECTおよびHTTPS通信の処理方式。
- プロキシを直列接続した際の通信互換性。
- APIレスポンス本文の取得可否。
- 証明書の信頼設定の必要性。
- ポート競合およびプロキシループの発生条件。

上記の構成が成立することを前提として実装を進めないこと。

成立しない場合は、代替構成または従来のJSON監視方式を採用する。

### 6.4 通信エンジンの技術選定

以下の2方式を比較検討する。

**方式A：完全C++実装**

候補ライブラリ：

- Boost.Asio
- Boost.Beast
- OpenSSL
- Qt Network

長所：

- Pythonランタイムから独立できる。
- 通信処理を細かく制御できる。
- ネイティブアプリケーションとして統合しやすい。

短所：

- HTTPSプロキシの実装難易度が高い。
- 証明書、HTTP CONNECT、HTTP/2、圧縮、接続管理等への対応が必要となる。
- 通信障害やセキュリティ上の問題が発生する可能性がある。
- 保守コストが大きくなる。

**方式B：C++本体と既存通信エンジンの連携**

通信エンジン候補：

- mitmproxy等の実績のある通信取得ソフトウェア。

通信エンジンは別プロセスとして実行し、必要なAPI情報のみをC++本体に渡す。

プロセス間通信には、ローカルソケット、名前付きパイプ、標準入出力等を検討する。

長所：

- HTTPS処理を一から実装する必要がない。
- 技術検証を比較的迅速に進められる。
- 通信処理とGUIの障害を分離しやすい。

短所：

- 外部通信エンジンへの依存が残る。
- 配布ファイルが増える可能性がある。
- 完全なC++単独構成にはならない。

**最終的には完全C++化を目指すが、初期の技術検証では方式Bを採用することも許容する。**

ただし、採用方式は実現可能性、安全性、保守性を比較した上で決定すること。

Boost.AsioやQt Networkを採用するだけでHTTPSレスポンスを取得できるわけではない点に注意する。

### 6.5 ブラウザ拡張機能方式

プロキシ方式が適切でない場合の代替候補とする。

ChromeまたはEdgeの拡張機能から、ブラウザが受信したAPI情報をC++本体へ渡す。

Chrome DevTools Protocol等を利用したレスポンス取得や、Native Messagingによるデスクトップアプリとの連携を検討する。

通常の拡張機能APIのみでは任意のレスポンス本文を取得できない場合があるため、実際に利用可能なAPIを確認すること。

この方式では独自ルート証明書を導入せずに済む可能性がある。

ただし、74EN内蔵ブラウザで同一の拡張機能が利用できることは保証されない。

初期リリースにおける必須機能とはしない。

### 6.6 74EN互換モード

現行のJSON監視方式を維持する。

Qtの `QFileSystemWatcher` 等を利用して対象フォルダの変更を監視する。

以下の事項を考慮すること。

- 新規ファイルの生成検出。
- 既存ファイルの更新検出。
- ファイルの書き込み完了前に読み込んだ場合の再試行。
- 同一ファイルの重複処理防止。
- 起動時に存在する古いJSONの一括再取り込み防止。
- ファイル更新時刻を使用した取得時刻の管理。
- ファイル監視イベントの欠落に対する補助的な確認。

独立動作モードが利用できない場合でも、従来方式へ切り替えることで使用できる構成とする。

## 7. データ保存およびログ管理

### 7.1 既存ファイルとの互換性

以下のファイルを原則として維持する。

| ファイル名 | 内容 |
|---|---|
| exp_log.csv | 提督経験値履歴 |
| ship_exp_log.csv | 全所持艦の総経験値履歴 |
| ui_config.json | 外観・表示設定 |
| first_setup_done.flag | 初回設定の管理 |
| last_cleanup.flag | JSON削除時刻の管理 |
| 74en_responses/ | 74EN互換モード用通信保存先 |

既存ファイルの仕様を変更する必要がある場合は、理由を説明し、移行方法を用意する。

過去の経験値履歴を消失させないこと。

### 7.2 経験値の重複記録について

同一の経験値が連続して取得された場合でも、原則として記録する。

これは、戦果周回を停止している時間や経験値が増加しない時間も、時速計測上の有効な観測時間となるためである。

以下のような記録を保持する必要がある。

```csv
timestamp,admiral_exp
2026-11-26T08:00:00,1000000
2026-11-26T08:05:00,1000000
2026-11-26T08:10:00,1000000
2026-11-26T08:15:00,1005000
```

同一経験値という理由だけで記録を破棄する実装は禁止する。

一方、同一通信イベントが複数回処理されることによる重複記録は防止する。

また、APIレスポンスを受信していない時間帯については、経験値が変化していないと断定できないため、根拠のない観測記録を自動生成しないこと。

### 7.3 メモリキャッシュ

起動時にCSVの経験値履歴を読み込み、必要なデータをメモリ上に保持する。

新規取得時にCSVへ追記し、メモリキャッシュを更新する。

現行仕様を維持しつつ、時速計算に必要な時間範囲を効率的に管理することを検討する。

ただし、初期段階でSQLite等への移行や自動圧縮を行う必要はない。

### 7.4 JSON自動削除

74EN互換モードにおいてのみ、現行の自動削除機能を維持する。

- 1時間に1回、削除条件を確認する。
- 最終更新時刻から48時間を経過したJSONを削除する。
- 初回起動時は削除時刻のフラグのみを作成する。
- 初回起動時には削除処理を実行しない。
- 削除対象は本ソフトウェア用として指定された保存フォルダ内に限定する。

独立動作モードでは、原則として通信レスポンスの全文をJSONファイルとして保存しない。

計測に必要な経験値データのみをCSVへ保存する。

## 9. 74ENのウィンドウ取り込み機能への対応

74ENには、外部アプリケーションのウィンドウを取り込む機能が存在する。

現行のPython版では、常に最前面に表示する設定が有効な場合に、取り込み時にウィンドウが消失する不具合が報告されている。

現在は、最前面表示を無効にしてから取り込むことで回避する仕様となっている。

C++版ではQtおよびWin32 APIを活用し、互換性の向上を図る。

検討対象：

- HWNDの取得および管理。
- ウィンドウスタイルの変更。
- WS_CHILDおよびWS_POPUP等の状態。
- WS_EX_TOPMOST等の拡張ウィンドウスタイル。
- 親ウィンドウが変更された場合の挙動。
- DPIスケーリング。
- フォーカス制御。
- ウィンドウサイズの固定および調整。
- ウィンドウ再生成に伴うHWNDの変更。

Qtのウィンドウフラグ変更によってネイティブウィンドウが再生成される可能性にも注意する。

ただし、74ENの実際の取り込み方式については、現行の公開ソースコードを確認した上で対応すること。

74ENが特定のWindows APIを使用していると未調査の段階で断定しない。

C++化のみで取り込みに関する問題が解決すると判断してはならない。

実際の74EN環境で取り込み、取り込み解除、設定変更、タスクトレイへの格納および復帰を検証すること。

## 10. セキュリティおよび通信上の制約

本ソフトウェアは経験値計測を目的とする受動的な情報取得ツールである。

以下の原則を遵守する。

1. ゲームへのリクエスト内容を書き換えない。
2. ゲームサーバーからのレスポンス内容を書き換えない。
3. ゲームサーバーへの独自APIリクエストを送信しない。
4. ゲーム操作の自動化を行わない。
5. APIトークンやCookie等の認証情報を永続化しない。
6. 取得した個人データを外部サーバーへ送信しない。
7. ローカル通信機能は原則として127.0.0.1に限定する。
8. TLS証明書の検証を無効化しない。
9. 証明書の導入が必要な場合は利用者の明示的な同意を得る。
10. 証明書を使用する場合は秘密鍵の保護および安全な削除手順を考慮する。
11. 通信エラー時にゲーム通信が破損することを避ける。
12. システム全体のプロキシ設定を無断で変更しない。
13. プロキシ設定を変更する機能を実装する場合は、設定復元手段を用意する。

HTTP CONNECTによる単純なHTTPSトンネルの中継だけでは、暗号化されたAPIレスポンスの本文を取得できない点に留意する。

HTTPSの取得方式については、実装前に技術的な成立条件と安全性を検証すること。

また、ゲームの利用規約および外部ツールに関する規定を確認すること。受動的な通信取得であっても、利用規約上問題がないことやアカウントへの制限が発生しないことを保証してはならない。

## 11. 将来的な拡張機能

以下は将来的な開発対象であり、C++版の初期移植における必須機能とはしない。

### 11.1 艦娘個体別育成管理

艦娘には、所持艦の個体を識別する `api_id` が存在する。

同名艦を複数所持している場合でも、個体IDによって区別できる。

利用する情報：

| API項目 | 内容 |
|---|---|
| api_id | 所持艦の個体ID |
| api_ship_id | 艦娘のマスタID |
| api_lv | 現在レベル |
| api_exp[0] | 累積経験値 |
| api_mst_ship | 艦娘マスタ情報 |

利用者が個体IDを指定し、育成対象艦と目標レベルを登録できるようにする。

別途取得するマスタJSONによって、`api_ship_id` と艦娘名を対応付ける。

改装等によってマスタIDが変化した場合でも、個体IDに基づく追跡を維持する。

### 11.2 育成管理ウィンドウ

メインウィンドウとは別のウィンドウを使用する。

表示項目候補：

| 個体ID | 艦娘名 | 現在Lv | 目標Lv | 累積Exp | 状態 |
|---|---|---|---|---|---|
| 3415 | 鹿島 | 98 | 99 | 950,000 | 育成中 |
| 28273 | 香取 | 99 | 99 | 1,000,000 | 達成 |

上記のデータは表示例である。

将来的には残り必要経験値等も表示できる構成とする。

### 11.3 育成対象の永続化

ファイル名候補：

`ship_targets.json`

```json
{
  "ships": [
    {
      "api_id": 3415,
      "target_lv": 99
    },
    {
      "api_id": 28273,
      "target_lv": 99
    }
  ]
}
```

### 11.4 個体別経験値のCSV出力

ファイル名候補：

`ship_individual_exp_log.csv`

```csv
timestamp,api_id,api_ship_id,name,level,exp,target_lv
```

既存の `ship_exp_log.csv` は全所持艦の総経験値用であるため、個体別経験値の保存先には使用しない。

GoogleスプレッドシートやExcelで利用できるCSVを基本とする。

Google Sheets APIによる自動連携は初期実装の対象外とする。

## 19. 通信データの非改変性に関する最重要要件（追加）

本ソフトウェアは、ゲーム通信に対する読み取り専用の計測ツールとして設計すること。

通信取得処理において、ゲームのAPIリクエストおよびAPIレスポンスのアプリケーション層における内容を変更してはならない。

以下の処理を禁止する。

- APIリクエストの生成、改変、追加、意図的な再送および複製。
- APIレスポンスの改変、偽造および差し替え。
- APIパラメータの追加、削除および変更。
- ゲームの状態を変更する処理。
- ゲーム操作の自動化。
- 認証情報の収集および永続化。
- ゲーム通信の意図的な遮断および遅延。

通信取得処理と計測処理は明確に分離し、計測処理からゲーム通信を変更できない構造とすること。

プロキシ方式を採用する場合は、通信中継の前後でAPIリクエストおよびレスポンスの内容が変更されていないことを、テスト用通信によって検証すること。

また、通信経路への介入が不要な取得方式が利用可能な場合は、その方式を優先的に検討すること。

通信の非改変性を確保できない実装方式は採用しないこと。

### 21.2 開発目標

航海日誌拡張版と74ENの併用構造を参考に、独立通信取得および74ENとの併用を調査する。以下のリクエスト方向の構成を個別に評価する。

```text
A. ブラウザ → 戦果時速計測機 → 艦これサーバー
B. 74EN内蔵ブラウザ → 74ENプロキシ → 戦果時速計測機 → 艦これサーバー
C. 74EN内蔵ブラウザ → 戦果時速計測機 → 74ENプロキシ → 艦これサーバー
```

各構成について、プロキシの役割、TLSの終端位置、各クライアントが信頼する証明書、上流証明書検証、接続失敗時の挙動を確認する。構成図だけで実現可能と判断しない。

### 21.3 実装方針

中継用データと解析用データを分離し、中継層から解析層への一方向イベントで受け渡す。解析層から中継層へ戻る参照・コールバック・制御経路を設けない。初期対象は `/kcsapi/api_port/port` の成功レスポンスに限定し、既存の提督経験値および全所持艦経験値計算へ渡す。

中継時にリクエスト本文を解析・保存しない。認証情報、Cookie、APIパラメータを永続化しない。対象外通信については本文を解析層へ渡さない。

### 21.4 通信エンジン比較

以下を、保守状況、セキュリティ情報、ライセンス、TLS・HTTP対応、配布サイズ、運用依存関係および非改変試験のしやすさで比較する。

- C++ / Boost.Asio / Boost.Beast / OpenSSL
- C++アプリと Titanium.Web.Proxy を用いるC#通信エンジン
- C++アプリと LittleProxy を用いるJava通信エンジン
- C++アプリと mitmproxy 等の外部通信エンジン

完全C++化より安全性、保守性および通信互換性を優先する。ただし、プロセス間通信、ランタイム、追加配布物による負荷も比較に含める。

### 21.5 禁止事項

次の処理を禁止する。

- APIリクエストおよびレスポンスの内容変更、ゲームAPIの独自生成・追加送信・意図的な再送、APIパラメータの変更
- 認証情報の収集・永続化、通信データの外部データベース送信、ゲーム操作の自動化
- TLS証明書検証の無効化
- 利用者の明示同意を得ない証明書登録、システムプロキシ設定変更

参考実装に禁止機能がある場合は移植しない。証明書登録やプロキシ切替が必要な場合、事前説明と明示的な利用者操作を必須とし、登録範囲を最小化し、停止時に本ソフトが追加した設定だけを安全に解除できることを設計する。

### 21.6 検証要件

ローカルテストサーバーと試験専用証明書を用いて、以下を検証する。実ゲーム通信や実アカウントによる試験とは明確に区別して記録する。

- 中継前後のAPI本文一致
- HTTPメソッド、宛先、APIパラメータ一致
- 意図しないリクエスト生成・再送がないこと
- 74ENなし、74EN上流プロキシ、74EN下流プロキシ各構成
- TLS証明書検証を維持した試験
- 通信エラーおよびプロセス終了時の復旧
- 既存CSV互換性

ローカル試験で確認した事実と実機の74EN/ゲームで確認した事実を混同しない。試験用の自己署名CAはテスト端末・アプリの一時的なカスタム信頼設定に限定し、Windowsのユーザー/マシン証明書ストアへ無断登録しない。

参考コードを流用する場合は、著作権表示および依存ライブラリのライセンス条件を遵守する。

### 21.7 最終目標

74ENおよび航海日誌拡張版を必要としない単独動作と、既存74EN利用者との併用を目標とする。通信取得方式を変更しても計測機能とGUIの仕様を維持する。通信の非改変性、安全性および安定性を、完全C++化や処理速度より優先する。

## 22. Phase 6 併用検証の進捗

2026-11-26時点で、Titanium.Web.Proxy 3.2.0とloopback上のテストサーバーによるA/B/C直列通信、HTTP/HTTPS本文一致、ポート競合、プロキシ停止時の失敗、同じポートでの再起動復旧、子プロセス強制終了後のポート解放を検証した。加えて.NET 10.0.404 / Titanium.Web.Proxy 8.0.2の独立サイドカーを作成し、HTTP/HTTPSのローカル中継試験を実施した。HTTP/2有効時のHTTPS試験は接続が停止したため、調査を止めずHTTP/2を無効にしたHTTP/1.1経路で本文一致を再確認し、PASSした。プロキシ出力が経験値数値のみで、要求/応答本文を記録しないことも確認した。

この結果はローカル模擬試験であり、実74ENの上流/下流設定、内蔵ブラウザ、ウィンドウ取り込み、実運用TLS証明書、実ゲーム通信の非改変性を検証したものではない。HTTP/2互換性は未解決である。サイドカーはQtアプリへ未統合で、方式切替UI、安定したCA管理、明示同意UIも未実装である。したがってPhase 6は未完了で、Qt版を74ENの上流/下流に設定してはならない。未達事項の詳細は `PHASE6_COEXISTENCE_REVIEW.md` を参照すること。

利用者の手元で、CSVをexeと同じフォルダに置いた後の読み込みが確認された。CSVはアプリ起動時に読み込み、実行中のCSVファイル更新は監視しない。`74en_responses` 内の対象JSONは起動後のファイル作成・更新を監視する。

## 23. 追加仕様：通信非仲介型データ取得方式の優先採用

### 23.1 最重要設計要件

戦果時速計測機の起動状態に、艦これのゲーム通信および74ENの動作を依存させないこと。

本ソフトウェアが未起動、正常終了、異常終了、再起動した場合でも、通常ブラウザおよび74ENによるゲームプレイが継続可能な構造を最優先とする。

この要件に伴い、独自プロキシによる通信中継方式よりも、ブラウザが受信済みのAPIレスポンスを観測する方式を優先する。

### 23.2 第一検証対象：Chrome DevTools Protocol

通常ブラウザおよび74EN内蔵WebView2に対し、Chrome DevTools Protocol（CDP）を利用した通信監視方式の実現可能性を調査する。

参考資料：

- [Chrome DevTools Protocol Network](https://chromedevtools.github.io/devtools-protocol/tot/Network/)
- [Microsoft Edge WebView2: Debug WebView2 apps with Visual Studio Code](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/debug-visual-studio-code)
- [ElectronicObserverEN](https://github.com/ElectronicObserverEN/ElectronicObserver)

74EN内蔵ブラウザがWebView2を使用していることは、公開ソースコードから確認済みである。ただし、現行配布版における外部CDPクライアントとの接続互換性は未検証であり、実機検証を行うこと。

### 23.3 通信構造

通常ブラウザ使用時：

```text
艦これサーバー ⇔ Chrome / Edge
                       ↓
                  CDPによる観測
                       ↓
                  戦果時速計測機
```

74EN使用時：

```text
艦これサーバー ⇔ 74EN ⇔ WebView2
                            ↓
                       CDPによる観測
                            ↓
                       戦果時速計測機
```

ゲーム通信の経路に戦果時速計測機を組み込まないこと。

### 23.4 C++実装候補

- C++20
- Qt 6 Widgets
- Qt WebSockets
- Qt Network
- QJsonDocument

データ取得モジュールとして`CDPCapture`を実装し、既存設計の`ICaptureSource`インターフェースを利用すること。現状の実装に同インターフェースがない場合は、既存の74EN JSONファイル監視を含む取得元を同一インターフェースへ整理する。

### 23.5 セキュリティ要件

- CDPによる通信監視とレスポンス取得以外の操作を原則として禁止する。
- ゲーム操作の自動化を行わない。
- JavaScriptの注入およびゲームページの書き換えを行わない。
- リクエストのインターセプト、停止、書き換え、追加送信を行わない。
- CookieやAPIトークンを取得目的としない。
- 認証情報や不要な通信データを保存しない。
- デバッグインターフェースを外部ネットワークに公開しない。
- デバッグ設定の変更は利用者の明示的な同意を得ること。
- ブラウザのセキュリティ機能を無効化しない。
- CDPの接続対象をゲーム用ブラウザおよび対象タブに限定すること。

### 23.6 検証項目

- 計測機を起動せずにゲームをプレイできること。
- ゲームプレイ途中から計測を開始できること。
- 計測機の終了後もゲーム通信が継続すること。
- 計測機を強制終了した場合もゲーム通信が継続すること。
- 計測機の再起動後に再接続できること。
- 74ENおよび通常ブラウザの双方で動作すること。
- ゲーム通信の内容を変更していないこと。
- 不要な認証情報を保存していないこと。
- 74ENのウィンドウ取り込み機能と併用できること。
- 複数タブ、iframe、ブラウザ再起動時にも適切に接続先を管理できること。

### 23.7 代替方式

CDP方式が成立しない場合は、以下の順に検討する。

1. ブラウザ拡張機能によるレスポンス監視。
2. 74ENの既存JSON監視方式。
3. 74EN側の公式外部連携インターフェースの利用。
4. 独自プロキシ方式。

独自プロキシ方式は、ゲーム通信が計測機の起動状態に依存するという設計上の問題があるため、利用者の承認なしに主要方式として採用しないこと。

### 23.8 開発方針

通信非改変性、通信経路からの独立性、安全性、安定性を最優先とする。

CDPの利用可能性を確認するまでは、独自HTTPSプロキシの本格実装に着手しないこと。

本節は既存の第6節、第21節およびPhase 5・6において独自プロキシを優先方式とする記述より優先される。第21節・第22節のローカルプロキシ試験結果は過去の調査記録として保持するが、CDP採用判断や実74EN互換性の証拠とは扱わない。

## 24. 通信非仲介型方式への移行進捗

2026-11-26：第23節の追加に伴い、Qtアプリの通信プロキシ起動ボタン、設定画面、サイドカー起動・終了処理を本体から除去した。アプリは74ENが保存したローカルJSONを引き続き読み込む。`ICaptureSource`インターフェースを追加し、既存の`ApiFileCapture`をその実装として接続した。プロキシサイドカーと試験用プローブ、過去のローカル検証記録は開発履歴に保持し、製品UIからは起動できない。

CDP仕様の公開資料では、Networkドメインの`responseReceived`イベントで応答情報を受け取り、`loadingFinished`後に`getResponseBody`で本文を取得する観測経路を確認した。実装では対象URLを照合した応答本文だけを短時間メモリに置き、取得後すぐ経験値解析へ渡して破棄する。Cookie取得、リクエスト本文取得、通信停止・書換えに関わるCDPメソッドは使用しない。

Chrome 136以降は既定ユーザーデータディレクトリに対する`--remote-debugging-port`が無効となり、別ユーザーデータディレクトリを必要とする。このため、利用中の標準プロフィールへ無断でCDPポートを追加する方式は採らない。WebView2はホスト側の起動引数等でCDP公開が必要となる。74ENの公開ソースではWebView2環境生成と`AdditionalBrowserArguments`の設定を確認したが、現行配布版で外部クライアントが接続可能か、追加デバッグポートを既存設定と安全に共存させられるかは未確認である。

現段階でCDPCaptureのプロトコル接続実装、接続対象選択UI、通常ブラウザおよび74EN実機での接続試験は未完了である。Qt環境にはQt6Networkがあるが、Qt6WebSocketsは確認できていない。次段階では依存モジュールの導入可能性を確認したうえで、まずローカルのテストブラウザと模擬APIで観測プロトタイプを検証し、その後利用者が明示同意した環境で74EN配布版との接続可否を確認する。デバッグポートをLANへ公開せず、ゲームプレイ継続性を必ず確認する。実機確認前にCDP方式を完成済みと記載しない。
