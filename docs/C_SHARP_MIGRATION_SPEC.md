# SenkaSpeedMeasuringDevice Ver.2
# 開発方針変更指示書・C#移行仕様書

## 0. Codexへの指示

現在、戦果時速計測機（SenkaSpeedMeasuringDevice）のC++移植および独立通信取得機能の開発をPhase 6まで進めている。

しかし、その後の技術調査および設計方針の再検討により、以下の2点について開発方針を変更することとした。

1. 開発言語をC++からC#へ変更する。
2. 独自プロキシによる通信中継方式ではなく、通信非仲介型のAPIレスポンス取得方式を優先する。

本指示書は、これまで提示した開発仕様書、追加仕様書および実装計画のうち、上記の変更に関係する部分を上書きするものである。

変更対象外の既存仕様については、従来の仕様書を引き続き有効とする。

既存のC++版を単純に削除して新規開発を開始するのではなく、Phase 6までに得られた開発成果、テスト結果、技術調査結果を可能な限り再利用すること。

プロジェクト名：

SenkaSpeedMeasuringDevice（戦果時速計測機）

GitHubリポジトリ：

https://github.com/rinopap/SenkaSpeedMeasuringDevice

対象OS：

## 2. 開発方針変更の背景

### 2.1 C++を採用していた理由

従来は、以下の目的からC++20およびQt 6 Widgetsを採用していた。

- 常駐時の軽量性向上。
- Pythonランタイムからの独立。
- Windows APIとの親和性向上。
- 独自HTTP/HTTPSプロキシの実装。
- 74ENのウィンドウ取り込み機能との互換性向上。

これらの目的自体は引き続き有効である。

### 2.2 通信方式の再検討

独自プロキシ方式では、戦果時速計測機がゲーム通信の経路上に存在することになる。

従来想定していた構成：

```text
艦これサーバー
      ↕
戦果時速計測機プロキシ
      ↕
74ENまたは通常ブラウザ
```

この構成では、戦果時速計測機の未起動、異常終了、通信処理の不具合等によって、ゲーム通信そのものが停止する可能性がある。

しかし、本ソフトウェアはゲームの動作に必要なソフトウェアではなく、あくまでも経験値を観測するための計測器である。

そのため、ゲーム通信を中継せず、既に受信されたAPIレスポンスを読み取る方式を優先することとした。

### 2.3 C#への変更理由

通信非仲介型の方式を採用する場合、主な処理は以下となる。

- WebSocket通信。
- JSON解析。
- 経験値の差分計算。
- CSV保存。
- GUI更新。
- Windows APIとの連携。

これらの処理に対してC++の低レベル制御能力は必須ではない。

一方、C#および.NETは非同期処理、WebSocket通信、GUI、Windows API、プロセス間通信等の開発に適している。

また、74EN自体がC#で実装されていることから、公開ソースコードの参照や将来的な連携機能の検討にも適している。

以上の理由から、開発効率、保守性、安全性および拡張性を重視し、C#への移行を行う。

## 3. 最重要設計要件

以下の要件を、使用言語や処理速度よりも優先すること。

### 3.1 ゲーム通信からの独立性

戦果時速計測機が以下の状態にあっても、通常ブラウザおよび74ENによるゲームプレイが継続可能であること。

- 未起動。
- 正常終了。
- 強制終了。
- 異常終了。
- 通信取得処理の停止。
- 再起動。
- CSV書き込みエラー。
- GUIの応答停止。

戦果時速計測機の動作をゲーム通信の成立条件としてはならない。

### 3.2 通信の非改変性

本ソフトウェアは読み取り専用の計測ツールとする。

以下の処理を禁止する。

- ゲームAPIリクエストの生成。
- ゲームAPIへの独自送信。
- APIリクエストの追加、改変、複製、意図的な再送。
- APIレスポンスの改変、偽造、差し替え。
- APIパラメータの変更。
- ゲーム操作の自動化。
- ゲームページへのJavaScript注入。
- ゲーム状態を変更する処理。
- 認証情報の収集および永続化。
- ゲーム通信の意図的な遮断または遅延。
- 取得したゲームデータの外部サーバーへの送信。
- TLS証明書検証の無効化。
- ブラウザのセキュリティ機能の無効化。

### 3.3 74ENへの非依存性

74ENがインストールされていない環境でも、本ソフトウェアを利用できることを最終目標とする。

ただし、74ENとの互換性は維持する。

74EN本体の改造や独自ビルドを必要としない連携方式を優先する。

### 3.4 設計上の優先順位

以下の順序で判断すること。

1. ゲーム通信の非改変性。
2. ゲーム通信からの独立性。
3. セキュリティ。
4. 動作安定性。
5. 74ENとの互換性。
6. 保守性。
7. 軽量性。
8. 処理速度。
9. 配布サイズ。

## 7. 通信取得方式の変更

### 7.1 採用方針

独自プロキシを主要通信取得方式とする従来方針を変更する。

以下の方式を検討する。

| 取得方式 | 位置付け |
|---|---|
| CDPによる通信観測 | 第一検証候補 |
| 74ENのJSON監視 | 既存互換方式・初期実装 |
| ブラウザ拡張機能 | 代替方式 |
| 74ENの外部連携機能 | 存在する場合に検討 |
| 独自HTTP/HTTPSプロキシ | 主要方式から除外 |

通信を仲介するプロキシ方式については、C++版の既存実装を保存する。

ただし、利用者の明示的な承認なしにC#版へ移植しないこと。

通信非仲介型の方式が成立しない場合でも、独自プロキシ方式に自動的に戻してはならない。

### 7.2 通常ブラウザでの構成

```text
艦これサーバー
      ↕
Chrome / Edge
      │
      │ 受信済みAPIレスポンスの観測
      ↓
CDP / WebSocket
      ↓
戦果時速計測機
```

戦果時速計測機はゲームサーバーとブラウザの間に存在しない。

戦果時速計測機を終了しても、ブラウザとゲームサーバーの通信経路は変更されない。

### 7.3 74EN併用時の構成

```text
艦これサーバー
      ↕
74ENプロキシ
      ↕
74EN内蔵WebView2
      │
      │ 受信済みAPIレスポンスの観測
      ↓
CDP / WebSocket
      ↓
戦果時速計測機
```

74ENの既存プロキシ設定を原則として変更しない。

戦果時速計測機を74ENの上流または下流プロキシとして配置することを必須としない。

## 8. CDP通信取得機能

### 8.1 基本仕様

Chrome DevTools Protocolを使用し、ブラウザが受信した通信レスポンスを観測する。

参考資料：

- https://chromedevtools.github.io/devtools-protocol/tot/Network/
- https://chromedevtools.github.io/devtools-protocol/
- https://learn.microsoft.com/en-us/microsoft-edge/webview2/
- https://github.com/ElectronicObserverEN/ElectronicObserver

C#ではClientWebSocket、HttpClientおよびSystem.Text.Jsonを使用することを基本とする。

### 8.2 使用するCDP機能

初期実装では以下の機能を中心に使用する。

| CDP機能 | 用途 |
|---|---|
| Network.enable | 通信監視の開始 |
| Network.responseReceived | レスポンス受信イベント |
| Network.loadingFinished | 受信完了イベント |
| Network.loadingFailed | 受信失敗イベント |
| Network.getResponseBody | レスポンス本文の取得 |
| Network.disable | 通信監視の終了 |

接続先タブおよびiframeを管理するために必要なTarget関連機能は、必要性を確認した上で追加する。

使用するCDPコマンドは明示的な許可リストで管理する。

### 8.3 使用禁止機能

以下に相当する操作は実装しない。

- Runtime.evaluateによるゲームページ上での任意コード実行。
- Fetchによるリクエストのインターセプト。
- APIリクエストの変更。
- レスポンスの差し替え。
- Network.replayXHR等による再送。
- Cookieの取得を目的とする処理。
- ブラウザの自動操作。
- ページ遷移やリロードの強制実行。
- 入力イベントの生成。
- キャッシュ設定や通信速度の変更。
- リクエストヘッダーの変更。

CDPが備える操作機能を使用してゲームへ干渉してはならない。

### 8.4 対象API

初期実装では以下のAPIのみを取得対象とする。

`/kcsapi/api_port/port`

対象URLは適切なゲームサーバーのホストおよびAPIパスに基づいて識別する。

単純な文字列の部分一致だけで無関係な通信を取得しないこと。

対象外のレスポンス本文を取得しないこと。

対象APIのレスポンス受信を確認した後、読み込み完了時に本文を取得する。

以下のケースも考慮する。

- Base64形式で返されるレスポンス。
- 大容量のレスポンス。
- レスポンス取得前のブラウザ切断。
- リダイレクト。
- iframe内で発生する通信。
- 同一タブ内の複数通信。
- レスポンス本文が既に破棄されている場合。

取得できなかったレスポンスについて、ゲームAPIを再送することは禁止する。

### 8.5 重複取得防止

同一通信イベントの二重取得を防止する。

CDPの接続セッション、対象タブ、requestId等を組み合わせて識別すること。

異なる通信イベントで同一の経験値が取得された場合には、双方を有効な観測記録として保存する。

経験値の値のみを根拠に重複判定してはならない。

### 8.6 通常ブラウザへの接続

ChromeおよびEdgeについて、外部CDPクライアントから接続する方法を調査する。

ブラウザのリモートデバッグ機能に関する最新の制約を確認すること。

必要に応じて、ゲーム専用ブラウザプロファイルの利用を検討する。

以下を遵守する。

- 利用者の同意なしにブラウザ設定を変更しない。
- 通常のブラウザプロファイルの安全性を損なわない。
- デバッグ接続先をローカル環境に限定する。
- ゲームに関係のないタブを監視しない。
- 計測機起動のためにゲームプレイ中のブラウザを強制終了しない。
- 利用者のログイン情報やCookieを移行・収集しない。

リモートデバッグの有効化にブラウザの起動時設定が必要な場合は、初期設定の段階で明示する。

既に起動している任意のブラウザへ無条件に接続できるとは想定しないこと。

### 8.7 74EN内蔵WebView2への接続

74ENの公開ソースコードでは、内蔵ブラウザにMicrosoft WebView2が使用されていることを確認済みである。

主要参考ファイル：

- Browser/WebView2Browser/WebView2ViewModel.cs
- Browser/BrowserViewModel.cs
- ElectronicObserver/Window/FormBrowserHost.cs
- ElectronicObserver/Observer/APIObserver.cs

ただし、現行74EN配布版に対して外部CDPクライアントが接続可能かどうかは、実機で確認されていない。

以下を調査すること。

- WebView2の外部CDP接続方法。
- WebView2のリモートデバッグ関連設定。
- 74ENを改造せずに必要な設定を適用できるか。
- 設定を適用するために74ENの再起動が必要か。
- 74EN内部で使用されるDevTools機能との競合。
- 複数WebView2インスタンスへの対応。
- 接続解除時のゲーム動作。
- 計測機の異常終了時の影響。
- セキュリティ上の問題。

74ENがWebView2を使用しているという事実と、外部CDP接続が可能であるという事実を混同しないこと。

外部CDP接続が成立しない場合は、74ENのJSON監視方式を維持する。

### 8.8 CDPのセキュリティ

CDPは読み取り専用の仕組みではなく、ブラウザ操作等も可能な強い権限を持つインターフェースである。

本ソフトウェアの実装を読み取り専用に制限することに加えて、デバッグインターフェースそのものの公開範囲についても検討する必要がある。

デバッグポートをローカルホストに限定した場合でも、他のローカルプロセスによるアクセスの可能性は残る。

安全な構成を確保できない場合は、ブラウザ拡張機能方式等の代替方式を検討すること。

## 9. 74EN互換モード

現在のJSON監視方式は廃止しない。

C#版ではFileSystemWatcherを使用して実装する。

対象フォルダ：

`74en_responses/`

対象ファイル：

`*api_port@port.json`

以下の仕様を維持する。

- 新規ファイルの生成検出。
- 既存ファイルの更新検出。
- 書き込み途中のファイルに対する再試行。
- 同一ファイルイベントの重複処理防止。
- 起動時の古いJSON一括取り込み防止。
- ファイル更新時刻を利用した記録。
- ファイル監視イベント欠落時の補助確認。
- 48時間より古いJSONの自動削除。
- 1時間ごとの削除条件確認。
- 初回起動時には削除処理を行わない仕様。

JSON削除は、本ソフト専用として設定されたディレクトリに限定する。

他のソフトウェアが管理するファイルやマスタJSONを誤って削除しないこと。

CDPモードとJSON監視モードを同時に有効化しないことを原則とする。

## 10. 既存計測機能の移植

### 10.1 提督経験値

取得対象：

`api_data.api_basic.api_experience`

戦果換算式：

```text
戦果増加量 = 提督経験値増加量 × 7 / 10000

戦果時速 = 戦果増加量 / 経過時間（時間）
```

この換算係数を変更しないこと。

### 10.2 表示対象時間帯

現在時刻が14:25の場合：

```text
12:00～13:00 戦果時速
13:00～14:00 戦果時速
14:00～14:25 戦果時速
```

過去2時間帯については、各時間帯の最初の観測記録と次の時間帯の最初の観測記録を使用する。

現在進行中の時間帯については、その時間帯の最初の観測記録と最新の観測記録を使用する。

実際の観測時刻間の経過時間を用いて計算すること。

記録不足、経験値の減少、経過時間が0以下の場合についても従来仕様を維持する。

新規通信が発生しない場合でも、時間帯表示は適切に更新する。

### 10.3 艦娘総経験値時速

取得対象：

`api_data.api_ship`

各所持艦の `api_exp[0]` を合計し、その時間差分から経験値時速を計算する。

現行方式では、艦娘の取得、解体、轟沈等によって所持艦構成が変化すると、総経験値に影響する。

これは既存仕様の制約であり、C#への移行に伴って無断で計算方式を変更しないこと。

### 10.4 データ型

累積経験値および総経験値にはC#のlong型等を使用する。

計算途中のオーバーフローに注意する。

### 10.5 経験値が変化していない場合

同一経験値が連続して観測された場合でも、記録する。

戦果周回を行っていない時間帯も、時速計測に必要な情報である。

同一通信イベントの二重処理のみを排除する。

取得できなかった時間帯について、観測していない経験値を推測して記録しないこと。

## 17. テスト仕様

### 17.1 計算処理テスト

次の入力を使用する。

```text
開始時刻：08:00
終了時刻：08:30
開始EXP：1,000,000
終了EXP：1,030,000

期待される戦果増加量：21.00
期待される戦果時速：42.00
```

以下も確認する。

- 経験値増加量が0の場合。
- 経過時間が0の場合。
- 経験値が減少した場合。
- 観測データが不足する場合。
- 日付を跨ぐ場合。
- 時間帯を跨ぐ場合。
- 32bit整数の範囲を超える経験値。
- 所持艦の総経験値の計算。

### 17.2 通信の非改変性テスト

ゲームサーバーへの実通信を使用する前に、ローカルのテストサーバーを用いて検証する。

確認事項：

- HTTPリクエストの送信回数が変化していないこと。
- リクエスト本文が変更されていないこと。
- リクエストヘッダーが意図的に変更されていないこと。
- レスポンス本文が変更されていないこと。
- 独自のゲームAPIリクエストを生成していないこと。
- CDPコマンドが許可リスト内に限定されていること。
- 認証情報が保存されていないこと。

### 17.3 通信独立性テスト

| 試験項目 | 期待結果 |
|---|---|
| 計測機未起動 | ゲーム通信が成立する |
| プレイ中に計測機起動 | 計測開始 |
| 計測機正常終了 | ゲーム継続 |
| 計測機強制終了 | ゲーム継続 |
| 計測機異常終了 | ゲーム継続 |
| CDP接続切断 | ゲーム継続 |
| CSV書き込み失敗 | ゲーム継続 |
| 計測機再起動 | 接続・計測再開 |
| ブラウザ終了 | 計測機は接続待機 |
| 74EN終了 | 計測機は接続待機 |

なお、再接続時に過去のすべての通信を取得できることは要求しない。

未観測区間を推測して記録しないこと。

### 17.4 セキュリティテスト

- 不要な外部通信が発生していないこと。
- 認証情報がログに出力されていないこと。
- ゲーム以外のタブを監視していないこと。
- 対象外のAPIレスポンス本文を取得していないこと。
- ローカル以外へデバッグインターフェースを公開していないこと。
- ブラウザ設定を無断で変更していないこと。
- 異常なJSONによってプロセスが停止しないこと。

### 17.5 長時間動作試験

24時間以上を初期目標とし、可能であれば72時間以上の連続動作を試験する。

測定項目：

- 平均CPU使用率。
- アイドル時CPU使用率。
- メモリ使用量。
- メモリ使用量の時間変化。
- GUI応答性。
- API取得から表示更新までの遅延。
- 起動時間。
- 終了時間。
- 配布サイズ。

Python版、C++版、C#版を可能な限り同じ条件で比較する。

C#版がC++版より軽量であることを前提としない。

- CDPを読み取り専用に制限する。
- 74ENとの互換性を推測だけで判断しない。
- 実行していないテストを成功扱いしない。
- Windows実機が利用できない場合は、その制約を明示する。
- ゲームの利用規約上の適合性を無条件に保証しない。

## 21. 各Phaseの報告要件

各M-Phaseの作業終了時には、以下を報告すること。

1. 実装した内容。
2. 変更したファイル。
3. C++版から再利用した成果。
4. 設計上の判断および理由。
5. ビルド結果。
6. テスト結果。
7. 未実装機能。
8. 未検証事項。
9. 発見された不具合。
10. セキュリティ上の懸念。
11. 次のPhaseの実施内容。

特に、ソースコード上で確認した事実、ローカルテストで確認した事実、Windows実機で確認した事実を区別すること。

## 22. 最初に実行するタスク

まずM-Phase 0を実施すること。

現在のC++版がPhase 6まで進んでいるため、既存の実装および開発成果を精査し、再利用可能なものを特定すること。

以下を提出すること。

- 現在のC++版の機能一覧。
- Phase 0～6の達成状況。
- 現在実装されている通信方式。
- 現行ブランチおよび変更状況。
- C#への移植対象一覧。
- そのまま再利用できるテストおよび資料。
- 廃止または保留する実装。
- C#版の技術構成。
- 新しいソリューション構成。
- 74ENとのCDP接続に関する技術的課題。
- 移行作業の実装順序。
- 移行によって発生するリスク。

既存コードの保全と移行計画の整理を行い、その結果を報告してからM-Phase 1以降へ進むこと。

既存C++版の全面削除やmainブランチの書き換えは行わないこと。

## 23. 最終開発目標

本ソフトウェアは、以下の要件を満たすことを最終目標とする。

- C#および.NETによるWindowsアプリケーション。
- 74ENを使用しない環境での計測。
- 74ENとの併用。
- ゲーム通信を仲介しない。
- ゲーム通信を改変しない。
- 計測機の起動状態にゲーム通信を依存させない。
- 既存戦果時速計測機能の維持。
- 艦娘経験値時速計測機能の維持。
- 既存CSVとの互換性。
- 74ENのウィンドウ取り込みへの対応。
- 軽量かつ安定した長時間常駐動作。
- 将来的な艦娘個体別育成管理への拡張性。

本ソフトウェアはゲームの通信を操作するソフトウェアではなく、ゲームから既に取得された情報を観測・集計する計測器として設計する。

以上を新しい開発方針とする。
