## 1. 本仕様書の目的

これまでSenkaSpeedMeasuringDeviceでは、通常ブラウザおよび74ENに対応するCDP通信観測方式の開発を進めてきた。

しかし、CDP方式には以下の課題が存在する。

- ブラウザのデバッグ権限に伴うセキュリティ上の問題。
- Google認証との互換性。
- ブラウザごとの接続方式の相違。
- ブラウザ起動設定の変更。
- ブラウザ起動補助機能への依存。
- 利用規約上の不確実性。
- 実装および保守の複雑化。

本ソフトウェアは、元来74EN利用者向けの小型計測補助ツールとして開発を開始したものである。

そのため、通常ブラウザへの対応を一旦保留し、74ENが標準機能で取得・保存しているデータを利用する方式へ開発方針を変更する。

本仕様書は、74EN専用版の新しい上位開発仕様書とする。

従来のM-Phase開発仕様書は、計算、GUI、データ保全等の引き継ぐべき要件について引き続き参照する。

ただし、CDP、ブラウザ起動、認証管理、マルチブラウザ対応に関する要件は、本開発ルートでは保留または廃止する。

## 2. 製品理念

本ソフトウェアを次のように定義する。

**74ENが既に取得・保存した情報を読み取り、提督経験値に基づく戦果時速および艦娘獲得経験値時速を利用者のPC内で計測する、独立した補助ソフトウェア。**

最も重要な設計思想は、74ENおよび艦これのプレイ環境が先に存在し、本ソフトウェアを必要に応じて追加できることである。

以下を必須とする。

- 74ENを起動するために計測機を必要としない。
- 計測機を起動するために74ENの起動方法を変更する必要がない。
- 74ENの標準配布版を使用できる。
- 74EN本体を改造しない。
- 74ENのゲーム通信処理に介入しない。
- 計測機の停止および異常終了が74ENの動作に影響しない。
- 計測機を削除しても74ENの利用環境に影響しない。
- 可能な限り利用者による追加設定を要求しない。
- 計測機自身は外部ネットワーク通信を行わない。

対応環境の拡大より、独立性、軽量性、安全性および保守性を優先する。

## 6. 74ENデータベース仕様

### 6.1 データベースの位置

事前調査で確認した標準的な保存先：

```text
ElectronicObserver/
└── Record/
    ├── ElectronicObserver.sqlite
    └── ResourceRecord.csv
```

ただし、相対パスの基準、ポータブル版、インストール方法、作業ディレクトリ等による差異を調査する。

実際の保存先を固定的に仮定しない。

### 6.2 ApiFilesテーブル

事前調査で確認した主なカラム：

| カラム | 内容 |
|---|---|
| Id | API記録ID |
| ApiFileType | API記録種別 |
| Name | API名 |
| Content | 圧縮されたAPIデータ |
| TimeStamp | 記録日時 |
| Version | データ形式のバージョン |
| SortieRecordId | 出撃記録との関連付け |

ApiFileTypeは事前調査対象では以下の列挙型に対応する。

- Request = 0
- Response = 1

実際のデータベーススキーマ、保存形式およびバージョンを読み取り専用で確認してから使用する。

### 6.3 圧縮形式

事前調査対象では、ContentはUTF-8文字列をBrotli圧縮したBLOBとして保存される。

.NET標準の以下の機能を使用する。

```csharp
System.IO.Compression.BrotliStream
```

圧縮形式が74ENのバージョンによって異なる可能性を考慮する。

未対応形式を推測によって無条件に解析しない。

### 6.4 JSON保存設定との独立性

APIObserver.csの事前調査では、SQLiteへの保存処理と、設定による個別JSONファイル保存処理は独立している。

したがって、個別JSONファイル保存機能が無効であっても、SQLiteから必要なデータを取得できることを目標とする。

実際の74EN正式配布版でこの動作を確認する。

## 7. SQLite読み取り専用アクセス

### 7.1 使用ライブラリ

既存C#版の依存関係を調査し、必要に応じてMicrosoft.Data.Sqliteを使用する。

74ENの内部実装を参照するためだけに、74EN本体のアセンブリやEntity Framework全体への依存を追加しない。

### 7.2 接続方式

必ず読み取り専用モードで接続する。

接続設定例：

```text
Data Source=<74ENのSQLiteファイル>;
Mode=ReadOnly;
Pooling=False;
```

実際の接続設定については、使用するSQLiteライブラリの仕様を確認する。

### 7.3 許可する操作

- 対象テーブルの存在確認。
- スキーマの確認。
- 必要なレスポンス記録のSELECT。
- 読み取り専用での記録IDおよび記録日時の確認。
- 対応バージョンの確認。

### 7.4 禁止する操作

- INSERT。
- UPDATE。
- DELETE。
- CREATE。
- ALTER。
- DROP。
- VACUUM。
- データベースマイグレーション。
- インデックスの追加。
- ジャーナルモードの変更。
- WALチェックポイントの強制実行。
- 74ENのデータベース管理設定の変更。

読み取り専用接続は、アプリケーション側でも書き込み経路が存在しないことを確認する。

### 7.5 ロック競合への対応

読み取り専用接続であっても、SQLiteの読み取りと74ENの書き込みが競合する可能性がある。

以下を実装する。

- 短時間の読み取り処理。
- 有限の待機時間。
- 件数を制限したバッチ取得。
- データベース競合時の再試行間隔。
- 長時間の読み取りトランザクションの禁止。
- 取得したBLOBの解凍およびJSON解析は接続終了後に行う。
- 競合継続時は計測側の処理を保留する。

74EN自身の保存処理を優先する。

読み取り専用モードを解除して問題を解決してはならない。

WALを使用するデータベースについて、関連ファイルの取り扱いや読み取り専用接続の成立条件を検証する。

稼働中のSQLiteファイルだけを単純コピーして整合したバックアップと見なさない。

## 8. データベースの検出

### 8.1 初回検出

74ENの稼働状況および実行ファイルの位置から、既存データベースの保存先候補を検出する。

プロセス情報は、実行ファイルおよびデータフォルダを特定するための必要最小限の範囲で利用する。

プロセスメモリは読み取らない。

自動検出できない場合は利用者によるフォルダまたはファイル指定を許可する。

### 8.2 複数の74EN環境

複数の74ENインストール環境が存在する場合、無断でいずれかのデータベースを選択しない。

利用者に対象環境を選択させる。

異なるデータベースの計測履歴を無条件に統合しない。

### 8.3 データベースの検証

- 対象ファイルの存在。
- SQLiteファイルとしての妥当性。
- 必要テーブルおよびカラムの存在。
- データ形式の対応状況。
- ローカルファイルであること。
- 読み取り専用接続の成立。

ネットワーク共有等への接続は初期実装の対象外とする。

## 9. 新規レコードの取得

### 9.1 基本方式

定期的に対象データベースを参照し、新たに保存されたAPI記録を取得する。

初期更新間隔候補：

2秒

実測結果によって調整する。

更新間隔を短くすることによって、74ENの動作に悪影響を与えてはならない。

### 9.2 取得SQLの例

提督経験値取得時の基本形：

```sql
SELECT
    Id,
    TimeStamp,
    Version,
    Content
FROM ApiFiles
WHERE ApiFileType = 1
  AND Name = 'api_port/port'
  AND Id > @LastProcessedId
ORDER BY Id ASC
LIMIT @BatchSize;
```

実際のスキーマおよびクエリプランを確認する。

必要に応じて対象APIの許可リストを使用する。

SQLは固定されたクエリおよびパラメータによって実行し、利用者が任意SQLを入力できる機能は設けない。

### 9.3 差分取得

記録IDを利用し、既に処理済みのレコードを繰り返し読み取らない。

ただし、記録IDの再利用、データベースの復元、初期化、ファイル差し替え等を考慮する。

単純にIdの最大値だけを永続化して安全と判断しない。

### 9.4 永続カーソル

以下の情報を計測機自身の保存領域に管理する。

- データ取得元の識別情報。
- 最終処理済みレコードID。
- データベース形式のバージョン。
- 最終観測時刻。
- 処理状態。

取得元の識別情報にはCookieやAPIトークンを使用しない。

データベースの変更を検出した場合は、安全に計測区間を分離する。

### 9.5 初回起動時の履歴

既存データベースには過去の膨大なAPI記録が存在する可能性がある。

初回起動時に全履歴を無条件に読み込まない。

現行GUIで必要な直近3時間帯の計測に必要な範囲を基本とし、適切な時間範囲または開始カーソルを決定する。

計測開始以前の記録については、74ENの記録から取得した過去データであることを区別する。

### 9.6 取得欠損

処理失敗したレコードを理由なく処理済みとして扱わない。

再試行可能なエラーと、未対応形式等による恒久的な解析失敗を区別する。

恒久的な解析失敗が後続のすべての正常データ取得を妨げないようにする。

欠損の存在を利用者へ提示できる構造とする。

## 10. 提督経験値および戦果時速

### 10.1 対象API

```text
api_port/port
```

SQLite内に保存されたレスポンスのみを利用する。

### 10.2 取得項目

```text
api_data.api_basic.api_experience
```

母港APIの保存時にapi_ship等が削減されることを考慮する。

提督経験値が保持されていることを実際のデータベースで確認する。

### 10.3 戦果換算

従来の計測式を維持する。

```text
増加戦果 = 提督経験値増加量 × 7 / 10000
```

```text
戦果時速 = 増加戦果 / 実観測経過時間（時間）
```

EO戦果、任務戦果等は従来仕様と同様に、この経験値由来の戦果時速へ加算しない。

74ENのSenkaViewerが表示する総戦果とは、計算対象が異なることに注意する。

### 10.4 観測時刻

原則としてSQLiteのTimeStampを使用する。

計測機がデータを読み取った時刻を観測時刻としない。

74ENのTimeStampは非同期保存処理の時刻であり、厳密なネットワーク受信時刻とは異なる可能性がある。

保存時刻の遅延および時間帯境界への影響を検証する。

### 10.5 既存計測仕様

従来の直近2つの確定時間帯および現在時間帯を表示する仕様を維持する。

各時間帯の最初の有効な観測と、次時間帯の最初の有効な観測、または現在の最新観測を利用する従来の計算方式を維持する。

実際の観測時刻差を分母に使用する。

観測していない値を補間して、架空の母港API観測を生成しない。

別々の母港API記録で経験値が同一の場合も、正常な観測として扱う。

## 11. 艦娘獲得経験値時速

### 11.1 採用方式

SQLite内に保存された戦闘結果等のレスポンスから、艦娘が獲得した経験値をイベント単位で集計する。

従来の全所持艦娘の累積経験値差分方式を、SQLite方式で無理に再現しない。

### 11.2 採用理由

74ENのApiFileService.TrimPortでは、母港API保存時に以下の処理を行っている。

```csharp
portResponse["api_data"]!["api_ship"] = new JsonArray();
```

したがって、標準SQLiteに保存された母港APIから全所持艦娘の累積経験値を直接取得することはできない。

一方、戦闘結果等のAPI記録はSQLiteに保存されているため、それらを利用して獲得経験値を集計する方式を採用する。

### 11.3 初期調査対象API

- api_req_sortie/battleresult
- api_req_combined_battle/battleresult
- api_req_practice/battle_result
- api_req_mission/result

これらは調査対象であり、すべての艦娘獲得経験値が取得可能であることを現時点で保証しない。

74ENのAPI型、戦闘結果解析、経験値表示および戦闘記録処理を確認する。

### 11.4 調査対象フィールド

候補：

- api_get_ship_exp
- api_get_ship_exp_combined
- api_get_exp
- api_get_base_exp
- api_mvp
- api_mvp_combined
- api_get_exp_lvup
- api_get_exp_lvup_combined

APIごとに実際の存在、型、配列構造、意味を確認する。

特に、api_get_expは提督経験値等を意味する場合があるため、艦娘経験値として一律に加算してはならない。

api_get_base_expについても、個々の艦娘の実獲得経験値と同一視しない。

### 11.5 経験値の定義

新方式では、艦娘の育成によって区間内に獲得した経験値を計測する。

以下は獲得経験値と区別する。

- 新規入手艦が既に保有している経験値。
- 解体によって失われた累積経験値。
- 近代化改修等によって失われた累積経験値。
- 轟沈によって失われた累積経験値。
- 単なるデータ更新に伴う既存経験値の再取得。

正常に獲得した経験値を、所持艦の減少によって減算しない。

### 11.6 計算式

```text
区間獲得経験値 = 対象区間内の有効な獲得経験値イベントの総和
```

```text
艦娘Exp時速 = 区間獲得経験値 / 経過時間（時間）
```

### 11.7 時間帯の取り扱い

獲得経験値イベント方式では、母港観測差分方式と時間帯の定義が異なる。

確定した時間帯については、原則として実際の時刻境界で区切る。

例：

- 12:00以上13:00未満。
- 13:00以上14:00未満。

現在時間帯については、その時間帯の開始時刻、計測可能になった時刻、取得済みデータの有効範囲等を考慮し、実際に評価可能な経過時間を使用する。

計測開始前や取得不能期間を、経験値獲得が0だった期間として無条件に扱わない。

同一イベントを複数時間帯へ加算しない。

時刻境界上のイベントについては、半開区間によって一意に所属時間帯を決める。

遅延保存されたレコードについては、該当する時間帯を再計算できる構造とする。

### 11.8 戦闘結果の解析

以下を個別に検証する。

- 通常艦隊。
- 連合艦隊。
- 遊撃部隊。
- 昼戦。
- 夜戦。
- 演習。
- 遠征。
- MVP。
- 旗艦補正。
- 戦闘評価による補正。
- 経験値上限に達した艦娘。
- 経験値上限へ到達する戦闘。
- 経験値獲得対象外の艦娘。
- 空きスロット。
- 配列先頭のダミー要素。
- 特殊なAPIレスポンス形式。

APIが既に補正適用後の経験値を返している場合、同じ補正を再度適用しない。

### 11.9 実獲得値との一致

API上の獲得経験値が、実際の艦娘累積経験値増加量と一致するかを検証する。

経験値上限等により一致しない場合は、その条件および補正可能性を整理する。

正確な実獲得経験値を算出できない場合は、推定値または取得可能な獲得経験値として明示する。

実際には確認できていない経験値を推測で補完してはならない。

### 11.10 未対応イベント

調査によって初期対象以外の経験値獲得イベントが存在することが判明した場合は、必要性を評価する。

未対応のイベントを黙って0経験値と扱わない。

集計対象が限定されている場合は、利用者向け説明に明記する。

## 12. 艦娘経験値方式の比較検証

### 12.1 検証目的

新方式で集計した獲得経験値が、従来の母港APIから得られる累積経験値増加量とどの程度一致するかを検証する。

### 12.2 比較方法

開発試験に限り、74ENのJSON保存機能による既存方式と新SQLite方式を併用する。

ただし、双方のデータを同一履歴へ二重記録しない。

それぞれ独立した検証用データとして保存する。

### 12.3 基本比較条件

以下の条件で比較する。

- 艦娘の入手がない。
- 解体がない。
- 近代化改修による艦娘消費がない。
- 轟沈がない。
- 経験値上限による影響がない。
- 比較区間内の必要な経験値獲得イベントが保存されている。

同じ母港観測区間を用いて、次の値を比較する。

```text
旧方式：全所持艦娘累積Expの増加量
新方式：区間内の獲得Expイベントの総和
```

単に各方式のGUI上の時速表示だけを比較しない。

計算区間を一致させて経験値そのものを比較する。

### 12.4 特殊条件の比較

以下について、従来方式と新方式の差を調査する。

- ドロップ・建造。
- 解体。
- 近代化改修。
- 艦娘喪失。
- 経験値上限到達。
- 演習。
- 遠征。
- 連合艦隊。
- 母港に長時間戻らないプレイ。
- 保存処理の遅延。
- データベースの取得欠損。

### 12.5 採用判定

通常条件において、経験値増加量が一致するか、差異の原因を説明できることを正式採用の条件とする。

特殊条件で差異がある場合は、指標の定義による意図した差異と、実装不具合による差異を区別する。

必要な経験値イベントが取得できない場合は、該当モードを実験機能または未対応として扱う。

## 13. データモデル

### 13.1 提督経験値観測

データ構造候補：

```csharp
public sealed record AdmiralExpObservation(
    long SourceRecordId,
    DateTimeOffset ObservedAt,
    long AdmiralExp
);
```

### 13.2 艦娘獲得経験値イベント

データ構造候補：

```csharp
public sealed record ShipExpGainEvent(
    long SourceRecordId,
    DateTimeOffset ObservedAt,
    long GainedExp,
    ShipExpGainKind Kind
);
```

### 13.3 経験値獲得種別

```csharp
public enum ShipExpGainKind
{
    Sortie,
    CombinedBattle,
    Practice,
    Expedition
}
```

上記は設計候補であり、実際の調査結果に応じて調整する。

### 13.4 共通データ管理

必要に応じて以下の情報を保持する。

- 取得元識別子。
- API記録ID。
- API種別。
- 74ENデータ形式バージョン。
- 観測日時。
- 計測アルゴリズムバージョン。
- 解析結果の信頼性。
- 欠損状態。

不要なレスポンス本文、艦娘名、提督名、認証情報等は保持しない。

### 13.5 数値型

経験値の合計には64bit整数型を使用する。

経験値を浮動小数点数として不必要に保持しない。

時速および戦果換算時に必要な浮動小数点計算を行う。

負の経験値、不正値、オーバーフローを検証する。

## 14. 重複記録および履歴管理

### 14.1 イベント識別

原則として以下の組み合わせによりイベントを識別する。

```text
取得元データベース識別子
＋ API記録ID
＋ 必要に応じた記録種別
```

記録IDだけでは異なるデータベースの記録を区別できないことに注意する。

### 14.2 重複排除

同一API記録を繰り返し読み取っても、獲得経験値を二重加算しない。

内容が同じ別API記録を、単に経験値が同一であることを理由として削除しない。

### 14.3 異常終了時の整合性

計測データの保存と最終処理済みIDの更新が不整合になった場合を考慮する。

アプリケーション再起動後に、以下が発生しない構造とする。

- 同一イベントの二重加算。
- 未保存イベントの永久欠損。
- 旧取得元と新取得元の履歴混在。

必要に応じて冪等な保存処理、永続イベントID、再構築可能な集計を用いる。

### 14.4 アカウント変更

同一74ENデータベースに複数アカウントの記録が存在する可能性を考慮する。

提督経験値の大幅な変化や取得元変更だけを根拠として、同一人物の継続記録だと判断しない。

アカウントを安全に区別できない場合は計測区間を分離するか、利用者による履歴切り替えを採用する。

アカウント識別のために認証情報を取得してはならない。

## 15. 既存CSVとの互換性

### 15.1 戦果時速用CSV

既存の提督経験値履歴を保全する。

```csv
timestamp,admiral_exp
```

既存形式を可能な限り維持する。

追加の取得元情報やイベント識別情報が必要な場合は、別の管理ファイル等を検討する。

既存履歴と新しいSQLite由来の履歴を統合する際は、観測時刻、重複、取得元の一致を確認する。

### 15.2 従来の艦娘経験値CSV

```csv
timestamp,ship_total_exp
```

これは全所持艦娘の累積経験値を記録したものである。

新方式の獲得経験値と同じ意味ではない。

したがって、このCSVへ新方式の獲得経験値を追記してはならない。

### 15.3 新方式のCSV

ファイル名候補：

`ship_exp_gain_log.csv`

形式候補：

```csv
timestamp,source_id,event_id,kind,gained_exp
2026-11-28T12:30:00+09:00,eo01,12345,Sortie,5400
2026-11-28T12:31:00+09:00,eo01,12358,Sortie,7200
```

上記は形式の例であり、値は合成データである。

### 15.4 履歴保全

- 既存CSVを削除しない。
- 既存CSVを無断で初期化しない。
- 累積経験値方式と獲得経験値方式を混合しない。
- 新旧方式を識別可能にする。
- データ形式を変更する場合は移行方法を文書化する。

## 16. プライバシーおよびセキュリティ

### 16.1 レスポンス限定

74ENのSQLiteにはリクエストとレスポンスの両方が保存されている。

本ソフトウェアは対象APIのレスポンス記録のみを読み取り対象とする。

SQLの取得条件でApiFileTypeを明示的に制限する。

### 16.2 データ最小化

以下の情報は取得・抽出・保存対象としない。

- APIトークン。
- Cookie。
- 認証情報。
- パスワード。
- リクエスト本文。
- 認証ヘッダー。
- 提督名。
- 計測に不要な個人情報。

対象レスポンスを解凍・解析する際、不要なフィールドが一時的に含まれる可能性はある。

不要なフィールドを列挙、抽出、永続化またはログ出力しない。

### 16.3 ログ

ログに記録する情報は以下を基本とする。

- 取得成功件数。
- 解析失敗件数。
- 最終正常観測時刻。
- データベース接続状態。
- 分類済みエラー。
- 対応形式の検証結果。

API本文全体やBLOBの内容をログに出力しない。

### 16.4 外部通信

計測機自身による外部通信を禁止する。

自動更新、アクセス解析、テレメトリー、外部エラー報告等を実装しない。

開発時の依存関係取得と、配布版の実行時ネットワーク通信は区別する。

### 16.5 利用規約

ゲーム通信への新規介入がないことは、ゲーム利用規約上の明示的許可を意味しない。

規約適合性やアカウント停止が発生しないことを保証してはならない。

運営への直接問い合わせは本開発工程の必須条件としない。

## 17. リソース管理

### 17.1 基本方針

本ソフトウェアは小型常駐計測機である。

74ENのプレイ体験を妨げないCPU、メモリおよびディスク使用量を目指す。

### 17.2 処理負荷

以下を実装する。

- 新規レコードのみの差分取得。
- API名および記録種別による事前フィルタリング。
- BLOBサイズ上限。
- Brotli解凍後のデータサイズ上限。
- JSON解析深度の上限。
- バッチ件数上限。
- 処理キューの上限。
- 一時データの速やかな破棄。
- 非同期処理。
- キャンセル処理。

具体的な上限値は74ENの実際の記録サイズおよび合成試験に基づいて決定する。

### 17.3 ポーリング間隔

初期値は2秒を候補とする。

高負荷時、データベース競合時、74EN未起動時は必要に応じて取得間隔を延長する。

同じ取得処理が重複して実行されないようにする。

### 17.4 GUIスレッド

SQLiteアクセス、Brotli解凍、JSON解析をGUIスレッド上で実行しない。

GUI更新頻度は必要最小限とする。

## 18. 監視状態

以下の状態を管理する。

| 状態 | 意味 |
|---|---|
| Disabled | 計測停止 |
| WaitingForDatabase | データベース待機 |
| Connecting | 読み取り専用接続の確認中 |
| Reading | 記録取得中 |
| Capturing | 正常な計測が可能 |
| DatabaseBusy | 74EN側の保存等による競合 |
| DataIncomplete | 取得欠損または未対応記録あり |
| UnsupportedDatabase | 未対応のスキーマまたは形式 |
| Error | その他の異常 |

名称は既存の状態管理構造に合わせて調整する。

74ENが起動していない場合も、既存の保存済み履歴を表示できるようにする。

74EN終了後に新規データが得られないことを、経験値獲得0として無条件に扱わない。

最終観測時刻を必要に応じて確認できるようにする。

## 26. 正式配布版の受入条件

以下を満たすこと。

- 74EN標準配布版で動作する。
- 74EN本体を改造しない。
- 74ENの起動方法を変更しない。
- JSON保存機能を必須としない。
- CDPを使用しない。
- ブラウザを起動しない。
- ゲーム通信に介入しない。
- 計測機自身による外部通信がない。
- SQLiteへ書き込まない。
- 74ENデータベースを削除しない。
- 認証情報を取得・保存しない。
- 提督経験値を正常に取得できる。
- 戦果時速が既存仕様と一致する。
- 艦娘獲得経験値の対応範囲が明確である。
- 艦娘獲得経験値の集計精度が検証されている。
- 取得欠損を正常な0経験値と混同しない。
- 同一イベントを重複集計しない。
- 異なる取得元の履歴を無断で統合しない。
- 既存利用者のデータを保全する。
- 計測機の終了によって74ENが停止しない。
- 対応74ENバージョンが明示されている。
- 既存機能の回帰試験が完了している。

艦娘獲得経験値時速が受入条件を満たさない場合、戦果時速のみを正式対応とする段階的な公開案を検討する。

不完全な艦娘経験値時速を正式対応済みとして扱わない。

## 27. Codexへの今回の実行指示

本仕様書を全文精読すること。

本チャットは、既存のCDP方式の開発チャットから分岐した74EN専用版の新規開発ルートである。

通常ブラウザへの対応およびM-Phase 14.1以降のCDP関連開発は一旦保留する。

既存の開発成果を保全した上で、74ENが標準機能で保存するSQLiteを利用した読み取り専用計測方式を研究・開発する。

今回の作業範囲はEO-Phase 0とする。

まず現在のリポジトリ、作業ツリー、既存実装、開発報告書、自動テストおよび74EN公式ソースコードを確認する。

特に以下を重点的に調査する。

- 現行74ENのSQLite保存処理。
- Brotli圧縮形式。
- 母港APIのTrimPort処理。
- 提督経験値の保存状況。
- 通常戦闘、連合艦隊戦闘、演習、遠征における艦娘獲得経験値の保存状況。
- 経験値フィールドの正確な意味。
- 実獲得経験値とAPI上の獲得経験値の相違。
- 経験値上限等の特殊条件。
- SQLiteから安全に取得可能な記録範囲。
- 既存計測コアとの統合方法。

ソースコードおよび合成データに基づいて、技術的成立性を評価する。

事前調査の内容を無条件に正しいと仮定せず、対象74ENバージョンにおいて再確認する。

必要に応じて独立した技術検証コードを作成してよい。

ただし、EO-0の段階で既存CDP実装を全面削除したり、製品GUIを大規模に変更したりしない。

EO_PHASE_0_RESEARCH_REPORT.mdを作成し、EO-1以降の具体的な実装計画を報告すること。

開発者による報告書の確認後、EO-Phase 1へ着手する。

以上を74EN専用版の開発統合仕様とする。
